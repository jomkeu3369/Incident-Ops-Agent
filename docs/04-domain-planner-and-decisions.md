# 04. 도메인 플래너와 근거 판정

Incident-Ops-Agent는 DR-DCI로 장애 로그와 런북에서 근거를 찾고, 근거를 인용한 복구 계획을 작성해 운영자에게 제안하는 멀티 에이전트 시스템이다. 판정 API는 **제안한 조치를 현재 근거가 뒷받침하는지** 확인하는 데 사용한다.

## 1. 장애 접수부터 운영자 승인까지

1. 총괄 에이전트가 장애 코드를 기준으로 A2A를 통해 로그 분석 에이전트에 조사를 요청한다.
2. 로그 분석 에이전트는 MCP로 해당 장애의 로그와 해당 서비스의 런북을 검색한다. DR-DCI 흐름에서는 메타데이터로 후보를 좁힌 뒤 필요한 본문만 가져오고, 계획에 사용할 근거와 청크 ID를 남긴다.
3. 복구 계획 에이전트가 [외부 API Tool](05-external-api-tools.md)로 롤백 후보, 후보 버전의 지표, 변경 금지 시간을 확인한다. 로그·런북과 조회 결과를 바탕으로 단계별 진행 조건, 조치, 인용한 청크 ID, 복구 확인 기준을 담은 초안을 작성한다.
4. 총괄 에이전트가 제안된 조치와 관련 근거를 판정 API에 전달한다. 근거가 충분하면 [계획을 등록하고 승인 요청을 생성](02-backend-api-and-mcp-spec.md#24-복구-계획-등록)한 뒤 AG-UI에서 운영자가 검토한다.

복구 계획의 저장 형식은 [DB 명세](01-architecture-and-db.md#23-remediation_plans-복구-계획)를 따른다.

## 2. 판정 API가 답하는 방식

첫 실험에서는 OpenAI Decisions API의 `POST /v1/decisions`와 `gpt-6-luna`를 사용했다. `input`에 제안, 로그, 런북 같은 공통 근거를 넣고 `questions`에 판단 기준과 답의 형식을 지정한다. API는 질문 순서대로 `answers`를 반환하며, 애플리케이션은 이 값을 사용해 다음 단계를 정한다. 동일한 근거를 평가하는 독립적인 질문은 한 요청에 묶을 수 있다. [OpenAI Decisions API 가이드](https://developers.openai.com/api/docs/guides/decisions#how-decisions-work)

| 질문 유형 | 반환값 | 장애 대응에서 쓸 수 있는 사례 |
| --- | --- | --- |
| `predicate` | 단일 조건이 참일 추정 확률 `0~1` | “이 로그에 DB 커넥션 대기 시간 초과 증상이 나타나는가?”를 물어 분석 대상 청크를 좁힌다. |
| `choice` | 선택한 항목, 항목별 확률, 확신도 | “현재 근거가 롤백 제안을 뒷받침하는가?”를 물어 운영자 검토, 근거 추가 조회, 계획 수정으로 분기한다. |
| `score` | 등급별 확률, 등급 번호의 가중평균, 확신도 | 장애 설명에 나온 사용자 영향을 `0: 영향 없음`, `1: 일부 지연`, `2: 결제 불가`로 평가해 검토 순서에 참고한다. |

`score`에서 세 등급의 확률이 10%, 60%, 30%라면 점수는 1.2다. 확신도는 별도 필드다. 공식 문서는 제품 사진의 손상 여부를 `predicate`로, 문의 유형에 맞는 부서 선택을 `choice`로, 소프트웨어 문제의 심각도 평가를 `score`로 설명한다. [질문 유형과 응답 해석](https://developers.openai.com/api/docs/guides/decisions#choose-a-question-type)

## 3. MVP의 판정 기준과 분기

첫 연동에서는 `choice` 한 종류로 계획의 근거를 판정한다. 입력에는 장애와 대상 서비스, 검토할 조치 한 건, 인용된 청크의 관련 부분을 담는다. 판정 모델에 묻는 질문은 “제공된 정보가 런북의 조치 제안 조건을 충족하는가?”처럼 관찰 가능한 기준으로 작성한다.

| 플래너 판정 | 판정 기준 | 총괄 에이전트의 다음 단계 |
| --- | --- | --- |
| `SUPPORTED` | 제출한 근거가 런북의 조치 제안 조건을 뒷받침한다. | 인용 근거와 확인 기준을 포함한 계획으로 운영자 승인을 요청한다. |
| `NEED_MORE_EVIDENCE` | 조치 제안 조건을 확인할 정보가 빠져 있다. | 대상 장애 범위에서 부족한 근거를 조회한다. 조회 한도를 소진하면 확인하지 못한 항목을 운영자에게 표시한다. |
| `CONTRADICTED` | 제출한 근거가 조치 제안 조건과 충돌한다. | 충돌하는 근거를 바탕으로 계획을 다시 작성한다. |

API가 실패하거나 답변을 거부하면 판정 불가로 처리하고 운영자에게 확인을 요청한다. 모델의 판정은 계획의 근거를 검토하는 데 사용한다. 조치에 대한 최종 승인·거절은 운영자가 AG-UI에서 결정하며, 백엔드는 [승인과 실행 결과를 기록할 때](02-backend-api-and-mcp-spec.md#3-핵심-비즈니스-규칙-incidentservicecompleteincidentwithpostmortem) 승인 ID, 대상 장애, 조치의 일치를 확인한다.

총괄 에이전트는 표의 세 판정값으로 분기한다. OpenAI Decisions API나 [TypeSafe Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev)를 연결할 때는 공급자의 응답을 이 판정값으로 변환한다. 확률과 확신도를 저장하거나 비교할 때는 사용한 공급자와 모델을 함께 기록한다. 공급자 교체 시에는 공통으로 정답을 표시한 장애 사례로 새 모델의 분류 결과를 확인한다.

## 4. 실험에서 확인할 것

예시 런북은 **새 배포 후 DB 커넥션 대기 시간 초과가 발생했고, 동일한 트래픽에서 이전 버전은 정상일 때** 롤백을 제안하도록 한다. 아래 세 사례에서 롤백 제안과 런북을 고정하고 근거만 바꾼다.

| 합성 사례 | 기대 판정 | OpenAI 첫 실험 결과 |
| --- | --- | --- |
| 커넥션 대기 시간 초과 로그만 있고 배포 이력은 없음 | `NEED_MORE_EVIDENCE` | `NEED_MORE_EVIDENCE` |
| 새 버전 배포 직후 오류가 발생했고 같은 트래픽에서 이전 버전은 정상 | `SUPPORTED` | `SUPPORTED` |
| 오류가 새 버전 배포 전에 이미 발생 | `CONTRADICTED` | 미실행 |

첫 실험은 로컬 `TEST/decision_demo.py`에서 앞의 두 사례로 API 요청과 선택지별 확률을 확인했다. 두 응답의 표시 확신도는 각각 100.0%였으며, 이 수치는 그 요청에 대한 모델 응답이다. 연동 전에는 세 판정별로 정답을 표시한 사례를 비교하고, 특히 근거가 부족하거나 충돌하는 사례가 `SUPPORTED`로 분류되는지 확인한다. [확신도와 임계값 검증 방법](https://developers.openai.com/api/docs/guides/decisions#interpret-the-answers)
